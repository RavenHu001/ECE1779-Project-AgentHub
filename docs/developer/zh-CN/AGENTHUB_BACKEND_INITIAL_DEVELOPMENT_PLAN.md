# AgentHub 最早期后端开发规划

更新日期：2026 年 10 月 11 日。状态：建议的首个开发里程碑。

2026 年 10 月 29 日实现入口：仓库已加入 Docker 后端骨架、四表迁移、固定回复 worker 和隔离测试；启动与团队使用方法见 [仓库英文 README](../../../README.md)。以下保留开发阶段的规划说明。

本阶段先建立一条能运行、能保存数据、能查询结果的后端基础链路：

**提交消息 → 保存消息和待办 → worker 领取 → 返回固定回复 → 保存并查询结果。**

它用于验证 FastAPI、PostgreSQL 和 Python worker 能一起工作。完整后端的目标和范围见 [后端总体规划](AGENTHUB_BACKEND_PLAN.md)；本阶段只实现其中最基础的一段。

## 本阶段要交付什么

使用接口测试工具提交一句“你好”，后端接收并保存。worker 处理后返回固定文字，例如“Message received.”，再通过查询接口看到原消息与回复。

固定回复是开发时的替代逻辑，不代表真实模型回答。之后在这个处理位置接入模型和业务工具。

本阶段的完成标准是：一名队员按说明启动服务、提交消息、查询结果、重启服务，并验证之前的记录仍然存在。

## 先准备哪些内容

### 确定最少的共同约定

先约定输入是一条文本消息、回复使用固定内容、工作只有等待处理、处理中、成功和失败几个阶段。记录之间要能够根据标识找到所属会话和原消息。

用户身份和会话归属从这里开始保留。可以先用预置测试用户进行本地开发；这只是开发身份安排，正式登录和访问检查仍要接入。消息请求中的 owner 不应由调用者随意指定。

本阶段的表名、路由和字段可以采用下面的建议，经团队统一后再写代码。它们不是原始项目规划已经确定的细节。

### 建立本地环境

先运行三个服务：

| 服务 | 本阶段的工作 |
| --- | --- |
| FastAPI | 接收消息、保存待办、查询历史、提供健康检查 |
| PostgreSQL | 保存测试用户、会话、消息和待办 |
| 一个 Python worker | 领取待办，产生固定回复并保存 |

使用 Docker Compose 一起启动它们，数据库挂载持久卷。提供示例配置、初始化步骤和简短 README，让队员能重复启动。

模拟业务服务在接入工单工具时加入，前端可以随后对接。当前先用接口测试工具验证这三个服务。

## 建议的最小数据和接口

### 数据记录

四张起步数据表的字段、类型、约束和关联关系见 [起步阶段四张数据表设计](AGENTHUB_BACKEND_INITIAL_DATABASE_DESIGN.md)。

| 记录 | 至少需要记住什么 |
| --- | --- |
| 测试用户 | 用户标识，以及会话属于谁 |
| 会话 | 会话标识、所属用户和创建时间 |
| 消息 | 所属会话、发言者、内容、顺序；回复对应哪条请求 |
| 待办 job | 来源消息、当前状态、领取信息、尝试次数及处理错误 |

任务执行档案、业务方案和审批记录在后续业务阶段加入。本阶段已经有持久待办，后续可以沿用其调度入口。

消息提交标识应保存下来，以便相同请求重发时找到原记录。领取信息应为后续限时领取和恢复留出位置；本阶段先运行一个 worker，不把多个 worker 的接管能力当作已完成。

### 接口入口

以下网址仅为起步建议，实际名称由团队统一：

| 入口 | 用途 | 应看到的结果 |
| --- | --- | --- |
| GET /health | 检查 API 和数据库连接 | 服务是否可用 |
| POST /conversations | 创建测试会话 | 会话标识 |
| POST /conversations/{id}/messages | 提交一条消息 | 已接收，以及消息和待办标识 |
| GET /conversations/{id}/messages | 查询会话消息 | 按顺序显示请求和固定回复 |

提交消息后先返回“已接收”，worker 在后台处理。前端或测试工具再查询结果。本阶段用普通查询验证链路，实时推送属于后续能力。

## 具体开发步骤

### 第一步搭起运行骨架

建立 API 与 worker 的独立启动入口，以及数据库配置和初始化方式。确认 API 能连接数据库，worker 也能读到待办记录。

完成标准：三个服务能够一起启动，健康检查可用，运行说明在另一名队员的环境中可复现。

### 第二步实现消息受理与查询

创建会话后，提交消息时一起保存消息和 job。两条记录应在同一个数据库事务中提交：要么都成功，要么都不保存。

相同提交标识重发时返回原受理结果，避免新建两条消息。查询接口只返回当前测试用户的会话内容。

完成标准：提交后能查到消息和对应待办；数据库失败时不会报告已成功接收。

### 第三步实现固定处理程序

worker 循环领取等待处理的 job，标记正在处理，读取原始消息，再由固定逻辑生成回复。

保存回复、把 job 标记成功应一起提交；回复关联原消息。失败时保存错误，便于定位。不要把记录只保存在 Python 内存里。

完成标准：提交一条消息后，worker 处理并退出这项工作，查询能看到一条对应回复。

### 第四步验证数据和基础错误

按下面的验收清单检查正常处理、重复提交、数据库不可用以及重启后的数据。发现问题后修复，再继续扩展功能。

完成标准：固定链路稳定，失败有明确记录，重新启动不会丢掉已保存的聊天。

### 第五步加入早期交付支持

从这一阶段开始配置基础 CI：运行已经存在的检查和有意义的测试，并构建容器镜像。写清环境配置、启动、初始化和接口调用方法。

有可运行骨架后配合云端负责人验证最小部署与存储，之后逐步扩展部署流水线。正式对外演示前接入相应身份验证、访问限制和 HTTPS。

完成标准：队员能复现本地流程，提交代码后能够自动检查和构建；云端工作按照总体计划早期开始。

## 验收清单

- 三个服务可以按说明启动，数据库数据存放在持久卷。
- 创建会话后，提交消息返回已受理及关联标识。
- 消息和待办一起保存，没有一半成功的记录。
- worker 处理待办，保存一条固定回复并结束这项工作。
- 查询结果能按顺序关联原消息与回复。
- 相同提交重发不新增消息或待办。
- 已完成的同一工作不重复生成回复。
- API 或数据库容器重建后，已保存的记录仍可查询。
- worker 暂时停止时，未领取的消息仍在待办中；重启后能继续领取。
- 处理错误有可追查的记录，README 和基础 CI 可用。

“worker 处理中崩溃后由其他副本安全接管”“业务动作成功但结果未保存”“审批后恢复”等场景，需在后续阶段完整验证。本阶段保留相关设计位置，但不能仅凭启动成功就声称已具备这些能力。

## 完成后接到哪里

这条基础链路完成后，沿总体规划逐步加入：

1. 模型调用和普通问答，保留固定模型替代程序用于重复测试；
2. 模拟工单、订单、资格判断，以及持续任务进度；
3. 具体方案、人工审批和模拟处置；
4. 重试、接管、防重复和 SSE；
5. 其余云端交付、安全、监控与备份恢复。

后续顺序可根据分工并行安排。权限和恢复规则应在对应功能设计时就考虑；涉及业务写入时，立即验证审批与防重复行为。
